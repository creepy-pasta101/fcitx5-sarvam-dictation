# Architecture

This document explains why the project is built the way it is. The message format itself is in [PROTOCOL.md](PROTOCOL.md); this file is about the shape around it.

## Two processes

Dictation needs three things that do not live comfortably in one place: a global hotkey inside the desktop's input framework, a microphone stream that has to be spawned, held open for as long as the user talks and then shut down cleanly, and an HTTPS request that can take seconds and can fail in a dozen ways. The first belongs inside fcitx5, because that is the only process that can see key events from every application and commit text into the focused field. The second and third belong anywhere but inside fcitx5, because fcitx5 runs a single event loop that also drives keyboard input for the whole desktop: a blocking read, a blocking `waitpid`, or a synchronous network call in an addon freezes typing in every window, not just the one being dictated into.

So the work is split. The C++ addon is a thin client — hotkey, socket, notifications, `commitString` — and is written so that nothing it does can block. The Python daemon is a separate process with its own asyncio loop, its own failure modes, and the freedom to spawn subprocesses and wait on the network. If the daemon crashes or hangs, typing keeps working; if fcitx5 restarts, the daemon keeps running and the next hotkey press reconnects to it. The two communicate over a Unix stream socket using newline-delimited JSON, and that protocol is the only thing they share.

The split also keeps the dependency budget honest. The addon links against fcitx5 and the C++ standard library and nothing else — no HTTP client, no JSON library, no TLS. All of that lives in Python, where the `sarvamai` SDK already exists.

## The addon in the input path

The addon is a **Module** addon, not an input method engine. That distinction is the single most important decision in the design. An input method engine is only fed key events while it is the *active* input method for an input context; when the user has switched to a different method, or when an application is using a plain keyboard layout, the engine sees nothing. Dictation has to work in whatever field the user is in, with whatever input method that field happens to be using, so an engine would defeat the entire purpose — you would have to switch to the dictation method before you could dictate, which is exactly the friction the tool is meant to remove. A Module addon has no such restriction: it is loaded once by the instance and can observe events globally.

The hotkey is therefore registered by watching key events on the instance, before the input method gets them:

```cpp
eventHandlers_.emplace_back(
    instance_->watchEvent<EventType::InputContextKeyEvent>(
        EventWatcherPhase::PreInputMethod, [this](KeyEvent &keyEvent) {
            // match the configured TriggerKey against keyEvent
        }));
```

`EventWatcherPhase::PreInputMethod` means the handler runs before the active input method sees the key, so a configured hotkey is ours to take regardless of what else is listening. When the key matches, the handler calls `filterAndAccept()` on the event — which stops it from reaching the application as ordinary typing — and starts the work. `KeyEvent::isRelease()` is checked first, because a release is not a toggle press: treating one as a press would fire the handler twice for a single physical key press, starting and immediately stopping the recording. Push-to-talk is the exception to that rule — its release is the event that ends the recording — and the section on the two interaction modes below explains what each kind of release does.

Handlers registered this way are owned by an `eventHandlers_` member of the addon, so they unregister when the addon is destroyed and cannot outlive the object that owns them. The trigger key itself is a `KeyListOption`, so the user can bind several combinations and can change them from `fcitx5-configtool` without restarting anything.

## Two interaction modes

One hotkey has two possible meanings, and the addon supports both: a key that toggles a recording on and off, and a key that records only while it is held. The wire protocol is unchanged between them. Push-to-talk is a `start` on the press and a `stop` or a `cancel` on the release, and all three commands already existed; the difference is entirely in how the addon reads key events.

**The toggle mode needs only presses.** A press starts a session, the next press ends it, and the addon keeps no more state than "a session is running". Presses are all it looks at, which is why the handler ignored releases for as long as this was the only mode.

**Push-to-talk needs the release event.** The duration of the clip is decided by the user's finger, and the only event that carries that information is the key-up. There is no timer the addon could run instead: the hold has no configured length, so the press can start a recording but nothing else can end it correctly. The handler therefore branches on `isRelease()` rather than returning early: a release of the push-to-talk key ends an active session, and a release of any other key is still ignored exactly as before.

**Auto-repeat has to be swallowed.** Both X11 and Wayland deliver a stream of press events while a key is held down, at the desktop's repeat rate. In toggle mode that is harmless, because a second press is a user action that means "stop". In push-to-talk it is destructive: every repeated press would arrive while a session is already active, and each one would send a fresh `start` with a new request id — dozens of times a second — restarting the recording under the user's finger and, in the worst case, having the daemon reject the extra starts as `busy`. So a press of the push-to-talk key that arrives while a session is already active is accepted and discarded: `filterAndAccept()` with no command sent. The event is still swallowed, because a held hotkey must not leak into the application as ordinary typing.

**A short tap becomes `cancel`, not `stop`.** Holding the key for a few tens of milliseconds is almost always a mis-keyed combination rather than speech. Sending `stop` would upload that fragment, ask the service to transcribe a fifth of a second of room tone, and commit whatever came back — possibly an empty string, possibly a hallucinated word — into the user's document. The addon therefore measures the hold against a 250 ms minimum and sends `cancel` when it falls short. `cancel` is the protocol's "discard this recording" command, so nothing is uploaded, nothing is committed, and the user sees nothing, which is the right outcome for an accident.

**Losing focus is turned into a release.** A key-up is delivered to whichever window has focus at that moment. If the user alt-tabs, clicks another window, or switches workspace mid-hold, the release goes somewhere the addon never sees, and the session would stay open until `max_duration_s` stopped it — several minutes of microphone with no way for the user to end it except another press. The addon therefore watches `InputContextFocusOut` and, when a push-to-talk session is active, treats the focus loss as the release it is never going to receive. The recording finishes with the same rule as a real release, so the audio captured up to that point is transcribed rather than thrown away.

**`cancel` is preferred whenever the daemon is not known to be recording.** On a release that passes the minimum hold, the addon does not send `stop` unconditionally: it sends `stop` only if the last `state` message the daemon broadcast said `recording`. If the state was anything else — the `start` failed outright, or the daemon already auto-stopped at `max_duration_s` — it sends `cancel` instead. The reason is that `cancel` is legal in every state, while `stop` against a daemon that is not recording produces a `busy` error. That error would arrive on top of the real failure the user has already been told about, and a second, misleading notification is worse than no second notification: it points at the wrong problem. Tracking the last broadcast state costs one member variable, set from every `state` message the handler already receives, and it is what makes that choice possible.

The two modes are also kept from interleaving. A press of the toggle key while a push-to-talk session is active is ignored — not filtered, just returned from — so a session cannot be started by one key and ended by the other, and the `stop`/`cancel` decision always belongs to the mode that opened the recording.

## Delivering the transcript

When the hotkey fires, the addon remembers the `InputContext` that had focus at that moment. It stores it as a `TrackableObjectReference<InputContext>` rather than a raw pointer, because transcription takes seconds and the user may close the window, switch workspaces, or quit the application while it runs — the input context can be destroyed before the answer arrives, and a raw pointer would then be dangling. A trackable reference knows when the object is gone.

When the `result` message arrives, the addon has to decide where the text goes, and that decision is the one part of delivery fcitx5 makes properly decidable:

```cpp
InputContext *ic = targetInputContext_.get();
if (!ic) { ic = instance_->mostRecentInputContext(); }
const bool canType = ic && ic->hasFocus();
```

**`commitString` can fail in more ways than it can report.** It returns `void`. There is no error to check, no acknowledgement from the application, and nothing the addon can observe afterwards: the call is a request that the frontend turn a string into a text-input event, and whether the application has a widget to receive it, and whether that widget keeps it, is settled on the far side of a boundary the addon cannot see across. The two failures that matter for dictation are a context that no longer exists — the window was closed, the application exited — and a context that exists but has no focus, which is what `mostRecentInputContext()` returns when nothing on the desktop is accepting input. The old code handled the first by typing into the second, which is how a sentence could land in another application, and the second by returning early, which is how a transcript could be dropped without a word.

**fcitx5 exposes `hasFocus()` and no "a text widget is focused" bit.** `InputContext::hasFocus()` exists (`fcitx/inputcontext.h:154`), and that is what the decision rests on. `InputContext::capabilityFlags()` also exists, and `CapabilityFlag` carries `SurroundingText`, `Preedit`, `Terminal` and more, but the flags are not a usable substitute for the missing bit. On X11 through XIM almost no client advertises `SurroundingText`, so reading "no surrounding text" as "not a text field" would redirect every terminal and most X11 applications to the clipboard — the fallback would fire constantly in exactly the places dictation is most useful. The rule the addon implements is therefore the narrow one that is actually decidable: **no focused input context means the transcript goes to the clipboard.** It is worth being plain about what that rule does not cover: an application that holds a focused input context and silently discards committed text — a browser page with no field focused, a file manager — looks exactly like one that accepts it, and cannot be detected. That gap is what the *Always copy the transcript to the clipboard as well* option is for, and no documentation of this addon should claim otherwise.

**The stale context is the dangerous case, not the missing one.** When the remembered context dies, the obvious repair is to type into `mostRecentInputContext()` and hope. That is what the addon used to do, and it is the wrong repair: the most recent context may belong to another application entirely, so dictating into an editor, alt-tabbing to a chat window while the transcription runs, and then watching the sentence appear in the chat window is a real sequence. Nothing is lost in that failure, which is what makes it worse than a dropped transcript — the text appears, in the wrong place, and can be sent before the user has read it. So an unfocused or absent context no longer means "guess again"; it means the clipboard, which is a place the user chose to paste from and where nothing can be sent by accident.

**An unfocused context is still attempted when the fallback is off.** With *Copy the transcript to the clipboard when nothing is focused to type into* turned off, the addon still calls `commitString` on a context it has but that lacks focus, because an unfocused context may accept a commit, and it falls back to the clipboard only when there is no context at all. The last resort is deliberately not switchable: an option can decide whether the clipboard is used instead of typing, but not whether a transcript is thrown away, because a user who turns the option off is asking for the old behaviour, not for silence.

**`ClipboardAlways` copies before it types, not instead of typing.** An application that has a focused context and discards commits is undetectable for the reason above, so the only useful option is one that does not depend on detection: with *Always copy the transcript to the clipboard as well* on, `deliverToClipboard` runs before `commitString` on every transcript. The ordering is the point. A copy made after the commit would be the one lost if the commit path did anything unexpected, and the whole purpose of the option is to have a copy that exists regardless of what the application does with the typed text.

**The clipboard tools get the text on stdin, which is why the spawn needs a pipe.** `wl-copy`, `xclip -selection clipboard` and `xsel --clipboard --input` all read the text from standard input; only Klipper, reached over D-Bus through `qdbus6`, `qdbus`, `qdbus-qt5`, `gdbus` or `busctl`, takes it as an argument. `buildClipboardCommand` therefore returns a bare argv for the three command-line tools and appends the text for the Klipper variants. Every other detached child in the addon — the daemon, `notify-send`, the OSD client — is spawned with all three standard descriptors on `/dev/null`, and for those tools that is correct, because they carry their whole input in their arguments. A clipboard tool given `/dev/null` on stdin would read end-of-file and put an empty string on the clipboard, silently. So the spawn uses `runDetachedWithInput`: the pipe is created before the fork, the read end is `dup2`'d onto `STDIN_FILENO` in the child, and the parent writes the text and closes the write end. A transcript is far smaller than a pipe buffer, so the write completes without the child having to read first, and a partial write is still handled rather than assumed away. `EPIPE` is ignored and reported as a failure, because a child that exits immediately would otherwise raise `SIGPIPE` — a signal whose default action would take fcitx5 down with it, over a clipboard copy.

**A successful copy is a state change, so it uses the recording indicator.** The copy is announced through `showRecordingIndicator` with the summary *Copied to clipboard* and a body saying that nothing was focused to type into. That is the same surface that reports recording state, and it is right for the same reason: the user caused this, the text is safe, and a small transient indicator is enough to say where it went. A notification would be the wrong instrument twice over — it is a large box that stays until dismissed and is filed in the tray history, and it would file an entry for something that worked. Notifications stay reserved for the failure they exist for: when no clipboard tool is found or the command cannot be started, the transcript really is lost, and `showErrorNotification` names the reason. The two outcomes are not the same event and do not share a surface.

If the trailing-space option is enabled and the text is non-empty and does not already end in whitespace, one space is appended to the *typed* text so that consecutive dictations do not run together. The clipboard receives the raw transcript, without that space: the space exists to separate text that is being typed, and a trailing space on a paste is only noise. An empty transcript commits nothing at all.

Tips run through the fcitx5 notifications module, declared as an *optional* dependency: every call is guarded by `if (auto *n = notifications())`, so the addon still works on a desktop where that module is not installed, just without the "Listening…" and "Transcribing…" tips. Those tips are off unless *Show a tip while recording* is enabled, and failures do not travel this way at all — they go to `notify-send`, for the reasons set out under the notification policy below.

## The notification policy

The addon used to announce itself: a tip on *Listening…*, a tip on *Transcribing…*, a tip closing when the daemon went idle. That is now off by default, and the reasoning is that dictation is used in bursts while the user is typing. A window that appears and disappears for every utterance competes for attention with the text being produced, and it carries no information the user does not already have — they know they pressed the key, and they can see whether text arrived. So the default is quiet: on most desktops nothing is shown while a recording is in progress, and the *Show a tip while recording* option exists only for users who want the old behaviour, in which case the existing tip helpers are used exactly as before, gated on that option instead of on the old notification option. The one exception is KDE Plasma, where a state change is reported through Plasma's own on-screen display; that is a different mechanism with a different argument behind it, and the next section is about it.

**A failed dictation is the one event that must reach the user.** Everything else in the addon's life is self-evident from the screen; a failure is not. The user has just spoken a sentence, released the key, and expects text. If nothing appears, the possibilities — the hotkey did not register, the daemon is not running, the API key is wrong, the microphone was muted, the transcript was empty — are indistinguishable from each other, and every one of them has a different fix. Silence here does not mean "nothing to report", it means the user is left guessing. That is why errors, and only errors, take a path that cannot be switched off by the tips option.

**`notify-send` rather than an fcitx5 tip.** Tips are delivered by fcitx5's notifications module, which the addon declares as an optional dependency precisely because it may not be installed or loaded. The case that matters most — something is broken — is also the case where the module is most likely to be unavailable or unhealthy, and a tip shown through a module that is not running is a tip nobody sees. So an error is handed to `notify-send`, a separate program that talks to the desktop's own notification service directly. The addon does not link libnotify and does not use its headers: it resolves the `notify-send` binary on `PATH` and executes it, which keeps the dependency budget at fcitx5 plus the standard library and means a missing libnotify is a missing program rather than a build failure.

The spawn is detached — a double fork with `setsid`, the same pattern used to start the daemon — with the three standard descriptors on `/dev/null`, so a notification daemon that hangs cannot block the fcitx5 event loop and the child cannot outlive its usefulness as a zombie. The addon never waits for the notification's exit status and never treats a failed delivery as an error of its own: a notification that does not appear is lost, not retried. The body is never written to a log, because it can carry an API error message and logs are shared more freely than screens.

**The fcitx5 tip is the fallback.** If `notify-send` is not on `PATH`, or the detached spawn fails, the error is shown as an fcitx5 tip instead — regardless of *Show a tip while recording*. That asymmetry is deliberate: the tips option is about how much the addon says while things work, and an error must never be dropped because the user asked for less chatter. The same rule makes the option ordering safe in every combination: desktop notification when the binary exists and *Notify on errors* is on, tip otherwise, and a warning in the log when both routes are unavailable.

## The recording indicator

The addon's answer to "is it recording?" is deliberately not a notification. On KDE Plasma, the start and the end of a recording are shown through Plasma's own on-screen display, the small centred indicator the desktop already uses for volume and brightness, and that is a different thing from the notification path described above.

**It is Plasma's OSD slot, not a notification.** Plasma exposes the indicator as a D-Bus method: `org.kde.osdService.showText(QString icon, QString text)`, on the session-bus service `org.kde.plasmashell` at the object path `/org/kde/osdService`. That is the call the desktop itself makes when the volume changes, so what the user sees while dictating is the same kind of element they already recognise. A notification would be the wrong instrument: it is a large box, it stays on screen until dismissed or times out, and it is filed in the tray's history, so a burst of dictation would leave a stack of entries saying that something was listened to. An OSD is transient and non-interactive — it appears, it fades, it leaves no record — which is exactly what a state change wants and exactly what it does not deserve more of. The text sent is the summary alone, `Listening` or `Transcribing`, never the explanatory body: a small centred indicator holds a couple of words, and the body exists for the tip, which is the surface with room for it. When the daemon reports `idle` the addon closes the tip as it always did and sends nothing to Plasma, because the OSD has already disappeared on its own.

**The addon shells out to a D-Bus client instead of linking one.** It tries `qdbus6`, `qdbus`, `qdbus-qt5`, `gdbus` and `busctl`, in that order, resolving the first one present on `PATH` once for the process lifetime and then running it detached, in the same way `notify-send` is run for errors. Each client has its own calling convention — the `qdbus` family takes service, path and method as positional arguments, `gdbus` wants `call --session --dest org.kde.plasmashell --object-path /org/kde/osdService --method org.kde.osdService.showText`, `busctl` wants the signature `ss` spelled out — so the argument vector is built per tool rather than assumed to be uniform. The alternative was to link Qt's D-Bus module or libdbus and make the call in-process, and it was rejected because it would add a build dependency, a header dependency and a version constraint to a C++17 addon whose entire dependency list is fcitx5 and the C++ standard library. A command-line client that a Plasma system normally has turns that into a program on `PATH` at worst, which is a missing indicator rather than a build failure — the same trade the error path already makes with `notify-send`. Because the child is detached and never waited on, the addon cannot block the event loop on a bus call either. The cost is per call, though, not per second, which is why the one path that would otherwise call it in a burst — the streaming partial transcript — is coalesced before it gets there, as the streaming section explains.

**A client that exits non-zero is deliberately ignored.** `qdbus6` is known to crash on exit on some Qt versions, after the OSD has already been shown. Its exit status therefore says nothing about whether the indicator appeared: the method call has been made and the display is up by the time the process falls over. Reporting that as a failure would put an error in front of the user for a dictation that worked perfectly, and the failure is not actionable anyway. So a non-zero exit is not an error, and because the child is never waited on the addon could not observe one even if it wanted to. The case it can still decide honestly is the other one: no client tool is installed at all, so nothing can be shown.

**Errors keep using `notify-send`.** The indicator is for a state change the user already caused, and it is allowed to be small and fleeting because of that. A failure is the opposite: the user expects text that did not arrive and has to read a reason and act on it. That has to be legible, it has to name the cause, and it has to still be there after the user has looked away and back, which is what a notification is for and what a fading centred glyph is not. So the error path is untouched — `notify-send`, with the fcitx5 tip as its fallback — and no failure is ever routed through the OSD.

Whether the OSD is used at all is decided once, cheaply. `isPlasmaDesktop` reads `XDG_CURRENT_DESKTOP` and `KDE_FULL_SESSION` from the environment: `KDE` has to be one of the colon-separated words of the former, compared case-insensitively, or the latter has to be non-empty, and a word that merely contains those three letters does not count. The answer is cached in a function-local `static`, because the environment does not change under a running fcitx5 and this decision is made on every state change. The order is: the OSD when *Show an on-screen display on KDE Plasma* is on and the session is Plasma; otherwise the fcitx5 tip when *Show a tip while recording* is on; otherwise nothing. On a desktop that is not Plasma the first branch can never be taken, so the option is inert there and the behaviour is what it was before the indicator existed.

## Reaching the daemon

The addon connects lazily, on the first hotkey press, and keeps the socket open afterwards. If the connect fails with `ENOENT` or `ECONNREFUSED` and autostart is enabled, it forks and execs the daemon command — detached with `setsid`, so the daemon survives an fcitx5 restart instead of dying with its parent — and then retries the connect every 200 ms for up to five seconds. The command that triggered all this is queued and flushed as soon as a connection succeeds, so the user's first press still starts a recording; if the retries run out, the pending command is dropped and a notification says the daemon is not reachable. At most one daemon is spawned per trigger, never one per retry.

Reads on the socket go through fcitx5's own event loop: `instance_->eventLoop().addIOEvent(fd, IOEventFlag::In, cb)` returns an event source owned by an addon member, and the callback reads whatever is available, appends it to a line buffer, and dispatches every complete line it finds. The socket is non-blocking, partial lines are kept until the newline arrives, and the buffer is capped at 1 MiB, matching the protocol's limit. A malformed line is logged and skipped — it never propagates as an exception into fcitx5's loop. After a disconnect the addon simply tries again on the next hotkey press.

A connection that has just succeeded is also sent a `reload`, so a daemon that has been running since long before the last configuration change picks that change up at the moment the addon first talks to it. That is the whole reason `reload` exists as a protocol command rather than the addon pushing values over the socket; the next section explains the reasoning.

## Configuration ownership

There are two processes and two kinds of setting, and the design rule is that each setting has exactly one file and that file has exactly one owner.

The daemon's settings — API key, model, mode, language, keyterms, streaming, audio device, sample rate, backend, socket path, maximum recording length — live in `~/.config/sarvam-dictation/config.toml`. The addon's own settings — trigger key, push-to-talk key, autostart, daemon command, the notification and indicator options, the clipboard options, trailing space — live in `~/.config/fcitx5/conf/sarvamdictation.conf`, which is an ordinary `FCITX_CONFIGURATION` block and therefore an ordinary fcitx5 addon page. `fcitx5-configtool` shows both groups on the one *Sarvam Dictation* page, so the user sees a single screen, but the values are persisted to the two files the two processes actually read.

The obvious alternative was to let the page push values to the daemon over the socket, and it was rejected for four reasons:

* **One file, one owner.** The daemon reads `config.toml`; the page writes `config.toml`. There is no third store of daemon settings to keep in step, and no code path where a setting exists in memory but nowhere on disk.
* **No divergence after a restart.** A daemon started by systemd, or restarted after a crash, reads `config.toml` and nothing else. If the page had pushed values over the socket, a restart would silently revert the daemon to whatever the file said — settings that appeared to be applied and were not. Writing the file makes the running daemon and the next daemon agree by construction.
* **No second copy of the API key.** A socket-pushed configuration would either carry the key over the wire into the daemon's memory and a second persistence path, or need a separate mechanism for the one value that matters most. Keeping the key in the 0600 `config.toml` and nowhere else means there is exactly one file to protect and one file to audit.
* **The daemon keeps working standalone.** The daemon has no dependency on fcitx5, on the addon, or on the socket being up in order to be configured. A user who installed only `pip install ./daemon` and runs it as a service edits `config.toml` and sends `reload`; the same loader serves both worlds, unchanged.

### The flow

1. `fcitx5-configtool` edits the addon's `Configuration` object. Both groups of options are in it: the daemon options are ordinary fcitx5 options that happen to be persisted elsewhere.
2. When the addon loads its configuration, it fills the daemon options from `config.toml`. A missing file leaves them at their defaults and is not an error; a file that cannot be parsed leaves the options untouched and logs the reason.
3. On *Apply*, the addon writes `config.toml` from the daemon options: parent directories created, a temporary file in the same directory, `fsync`, rename, mode `0600`. The atomic write matters because a half-written config file is a file the daemon may read.
4. The addon then sends `reload` on the socket. The daemon re-reads the file and applies it to the next recording. A recording already in progress finishes with the settings it started with, so pressing *Apply* mid-dictation never truncates or corrupts a transcript. If the file the addon just wrote is rejected, the daemon answers `config_invalid` and keeps its previous settings rather than failing.

The order in that list is the point: the file is written first and the notification comes second. The file is the state; `reload` is only a hint that it changed. A daemon that missed the hint, or was not running when it was sent, is still correct, because the next `reload` — or the next daemon start — reads the same file.

### The TOML layer

`src/tomlfile.{h,cpp}` is a small reader and writer for the subset of TOML this project needs: sections, bare and quoted keys, basic and literal strings with the standard escapes, booleans, integers and single-line or multi-line arrays of strings. It includes nothing but the C++ standard library — no third-party TOML library, in keeping with the addon's dependency budget.

Two properties of it matter for configuration ownership. It preserves keys it does not manage: a `TomlDocument` is parsed from the existing file, the eleven managed keys are set on it, and the document is serialised back, so a user's own comments-free extra keys, or a key a newer version understands and this one does not, survive an *Apply*. And it never fails to load: a line it cannot understand becomes a warning and is skipped, so a file written by a future version still opens in an older addon instead of being rejected wholesale.

### The value mapping

The addon does not hand-roll the conversion between TOML values and fcitx5 option values. It builds a `RawConfig` keyed by the option names and calls `config.load(raw, /*partial=*/true)` to read the file in, and `config.save(raw)` to get the values back out. Enums, booleans, integers and string lists are therefore marshalled by fcitx5's own rules rather than by a second implementation of them that could drift — an enum's stored name stays the same string the TOML file holds, and a `std::vector<std::string>` keeps being marshalled as indexed children (`Keyterms/0`, `Keyterms/1`, …) rather than a comma-joined string that would break on a keyterm containing a comma. Where the two formats genuinely differ — `True`/`False` in a `RawConfig` against `true`/`false` in TOML — the conversion is explicit and in one place.

### The audio device dropdown

The device setting is stored as a plain string, but the page does not ask the user to type one. `fcitx5-configtool` decides which widget to build from the option's description: an option whose description says `Type = Enum` becomes a combobox, its values read from `Enum/0`, `Enum/1`, … and its labels from `EnumI18n/0`, `EnumI18n/1`, …, with the scan stopping at the first index that has no value. That is the shape an ordinary enum option produces from a fixed C++ enum, and such a list is fixed at compile time — no use for a setting whose valid values are a property of the machine rather than of the program.

What makes a runtime-generated list possible is that the description is not written by the option class alone. `Option<T, Constrain>::dumpDescription` sets `Type` through the common option base and then calls the constrain's own `dumpDescription`, and for a plain `std::string` nothing afterwards overwrites what was written. A custom constrain can therefore emit `Type = Enum` together with its own `Enum/N` and `EnumI18n/N` entries, computed while the page is being built. The device option uses exactly that: its constrain emits a fixed first entry — the empty string, labelled *System default (follow the desktop)*, so the default is always selectable — and then one entry per device enumerated from the machine, with the id the capture tool wants as the value and the human-readable label as the text. Its `check()` accepts every string, because a device may be absent for an hour and the value must not be rejected for it.

The enumeration itself lives in the daemon rather than in the addon. The daemon is the half that already knows about capture backends and their command lines, it is written in Python, where parsing `pactl list short sources` and `arecord -l` is a few lines instead of a new dependency, and it can be exercised by the test suite with no fcitx5 running. The addon reaches it through the daemon's own command line — `sarvam-dictation-daemon --list-audio-devices`, which prints the same `id<TAB>label` lines to standard output and exits 0 even for an empty list — by forking and exec'ing the binary and reading its stdout through a pipe with a hard deadline of a few hundred milliseconds, killing and reaping the child if it overruns. Linking libpulse and ALSA and enumerating in-process was the alternative, and it was rejected for the same reason the OSD does not link libdbus: it would add two build dependencies, their headers and their version constraints to an addon whose entire dependency list is fcitx5 and the C++ standard library, and it would put a call that can block inside fcitx5's event loop. A subprocess with a deadline cannot stall the desktop, and a missing or broken daemon costs an empty list rather than a failed page. The result is cached for a couple of seconds, so building the page does not fork once per widget, and because the list is generated while the page is built, a device plugged in afterwards appears only when the page is reopened.

The configured device is injected into the list when the enumeration does not return it. Without that, a configured device that is currently unplugged would have no entry among the enumerated values, so the page could not show the setting it actually holds: the list would be one in which the configured value has no place, and the next *Apply* would rewrite `[audio] device` with whatever the page was displaying. So the addon reads the stored value from `config.toml` and, when it is not among the enumerated ids, adds an entry for it labelled with that value followed by *(not currently available)*. The page then shows a device that is configured but absent, which is what the situation is, and the setting survives an unplugged headset instead of being quietly changed by it. It also keeps the dropdown a view over a string rather than a second store of truth: the value stays a plain `std::string`, the TOML mapping above is unaffected, and a hand-edited `[audio] device` is still honoured.

### The API key field on the page

The key is the one daemon setting the configuration page cannot show. `fcitx5-configtool` renders an `Option<std::string>` as a plain `QLineEdit`, and the only option hints it understands are `Enum`, `EnumI18n`, `IntMin`, `IntMax` and `ListConstrain`: there is no password widget, no `EchoMode` to set and no `Password` hint to declare. Nothing on the addon side can make that line edit echo dots instead of characters, so a genuinely masked field cannot be obtained from the addon at all.

What the addon does instead is make the field write-only. When it loads `config.toml` and finds a key there, it copies the real value into a member and sets the option to the fixed sentinel `********`. The page therefore shows eight asterisks, and the key stays in the 0600 file where it has always been. On *Apply* the addon compares the option against the sentinel before it writes anything: equal means the user did not touch the field, so the remembered key is put back and saved unchanged; empty means the user cleared it, so the key is removed; anything else is a new key and replaces the old one. The sentinel itself is never written to `config.toml`, because a file whose `[api] key` was `********` would be a configuration that can only fail.

The cost is worth stating plainly, because the field looks like something it is not. It cannot reveal what is stored, only replace it: a user who has forgotten which key is configured cannot read it back from the page and has to paste a new one, and the field appears populated whenever a key exists without saying anything about which key it is. The alternative — showing the key in a plain line edit — would put it on screen in every screenshot of the settings page and in every screen share, which is a worse outcome than the inconvenience. It also explains why the option is described as write-only rather than masked: masking is what the toolkit would do, and the toolkit offers no way to ask for it.

## The daemon's audio pipeline

This section describes the REST path, which is what runs unless `[api] streaming` is on; the streaming path, and how it differs, is the next section.

Recording is a sequence of small, individually boring steps, and the order matters.

Capture is a subprocess: `pw-record`, `parec` or `arecord`, chosen by `detect_backend` according to `[audio] backend`, defaulting to whichever is first on `PATH`. The daemon does not link an audio library; a subprocess is one less thing to build against, and all three tools write a WAV the rest of the pipeline can read.

Stopping the capture is the delicate part. A WAV header written at the start of a file contains sizes that are only correct once recording ends, so a capture process that is killed outright leaves a header claiming zero or nonsense length — the audio is all there and none of it can be read. The daemon therefore shuts the child down gracefully: `SIGINT` first, wait up to three seconds, then `SIGTERM`, wait two, and only then `SIGKILL`. Every one of the three tools finalises its header on a polite signal; none of them does on `SIGKILL`. `SIGKILL` is the last resort, not the first.

The finished file is then normalised to 16 kHz mono 16-bit PCM, which is what the service expects and what keeps the chunk arithmetic predictable. The duration is read back from the normalised file rather than estimated from the process's run time, so `duration_ms` in the result is a measurement.

If the recording is longer than 28 seconds, it is split into ordered chunks with the standard library's `wave` module, each chunk transcribed separately, and the pieces joined: each part stripped, empty parts dropped, and the rest joined with single spaces. 28 seconds rather than 30 leaves headroom under the REST endpoint's roughly 30-second limit, so a chunk that is a few milliseconds over is still accepted. `segments` in the result reports how many chunks were used. `max_duration_s` (default 300) is a separate safety net: it stops the recording automatically, so a session the user forgot about cannot run until the disk fills.

The transcription call itself uses the `sarvamai` SDK, imported inside the method that needs it. That keeps the daemon importable, and its tests runnable, on a machine where the SDK is not installed; and it means a missing SDK surfaces as a transcription error at the moment of use rather than as a startup failure. The API key is read from `[api] key` or `SARVAM_API_KEY` before any network call is attempted, so a missing key produces `no_api_key` immediately rather than after a failed request. The key never appears in an error message or a log line.

## The streaming path

The pipeline above describes the REST path, which transcribes a finished file. Streaming is the second path. With `[api] streaming` on, the daemon opens a WebSocket to Sarvam's realtime endpoint when the recording starts, sends audio as it is captured, and forwards the interim text to the addon while the user is still speaking. The state machine, the ownership rules and the six commands are identical to the REST path; what changes is where the audio goes and when the text comes back.

**`endpointing="manual"` because the hotkey owns the utterance boundaries.** The realtime service can decide for itself when a speaker has finished, and for a general-purpose transcription tool that is the right default. In a dictation tool the decision has already been made by the user's finger: the recording starts on a key press and ends on a key release, and that hold is the utterance. Server-side endpointing would cut a sentence in two the moment the speaker paused to think — mid-hold, with no key event involved — and each cut would arrive as another final segment to be joined back together, at exactly the points where the model was least sure. Manual endpointing lets the daemon mark the start of speech when capture begins and the end of speech when the key is released, so the boundaries are the ones the user chose. It also keeps a long hold honest: a pause in the middle is silence inside one utterance, not the end of it.

**`linear16` removes the WAV and the normalisation step.** The REST path needs a file because a file is what it uploads: the capture tool writes a WAV, the daemon normalises it to 16 kHz mono 16-bit PCM, measures its duration, and only then can it be split into chunks and sent. The realtime endpoint's native input is exactly what that normalisation produces — raw little-endian signed 16-bit PCM, mono, at the configured sample rate — so the capture tool is asked for raw PCM on its standard output instead of a file, and the bytes go into the socket as they arrive. There is no header to finalise, no temporary file, no `wave` round-trip and no resampling pass, and the duration that `result` reports is measured from what was captured rather than read back from a normalised file. The graceful shutdown ladder survives, but for a different reason than on the file path: here it exists to reap the child cleanly and to stop the read loop, not to make a header readable afterwards.

**Two tasks: one drains, one receives.** A streaming recording needs two things to happen at once and neither may block the other: audio has to be read from the capture process and sent, and messages have to be read from the WebSocket. So the daemon runs two asyncio tasks per streaming recording. The drain task iterates the recorder's chunk iterator and feeds each chunk to the transcriber, and it ends when the child exits. The receive task reads from the socket and dispatches what comes back: partials go to the callback that decides whether to send a `partial` message, finals are collected so that the final transcript can be assembled in utterance order. Neither is a thread, because both jobs are I/O-bound and the loop already multiplexes them, which keeps the loop free to answer `ping` and to accept `cancel` throughout. On `stop` the recorder is stopped, which ends the drain task; the transcriber is then asked for its final transcript, both tasks are awaited, and the text goes out through the ordinary `result` path. On `cancel` both tasks are cancelled and the socket is closed, so a cancelled session leaves nothing running.

**Partials are throttled to about ten a second.** The service emits partials as fast as it recognises words, and each one would otherwise cost a socket write, a JSON parse in the addon and a D-Bus call to the on-screen display — the last being the expensive one, since it spawns a separate process per update. Ten a second is faster than anyone reads and slow enough that the indicator updates instead of flickering, so the daemon sends at most one `partial` per 100 ms and always sends the last text it has seen: nothing is lost but intermediate frames. A partial identical to the one last sent is dropped, because a pause in speech would otherwise produce a run of identical frames, each one paying for an OSD update to say the same thing. The final transcript does not travel this path at all; it is the `result` message, sent once, after throttling has stopped mattering.

**The partial display is coalesced on a trailing edge, and it shows the newest words.** Throttling in the daemon is only half of the cost. The addon used to call the on-screen display for every `partial` message it received, and each of those calls forks a D-Bus client and hands Plasma a fresh `showText`. Ten forks a second inside fcitx5's process is wasteful on its own, but the visible symptom is worse than the cost: Plasma restarts the fade-in animation on every `showText`, so a steady stream of updates makes the indicator flash in place instead of fading in once and holding. The addon therefore keeps the newest partial in a member and, if a timer is not already armed, arms a one-shot timer on the event loop — the same `addTimeEvent` mechanism the reconnect retry uses — for 350 ms. When it fires, the stored text is shown if it differs from what is on screen, and the timer disarms. That is at most three updates a second, and the newest text always lands. A trailing edge rather than a leading one is what gives that guarantee: the last partial always schedules a show, while intermediate ones are overwritten before they ever reach the bus.

Two smaller things happen on the same path, because a partial is service output rather than a message the addon wrote. It is sanitised before it is shown: whitespace runs collapse to a single space, control characters are dropped and the result is trimmed, since newlines and runs of spaces in a single-line centred indicator render as gaps or as nothing, and a partial that sanitises to nothing is not shown at all. Its length is capped to the tail — roughly the last 120 bytes, cut on a UTF-8 code-point boundary so a Devanagari or other multi-byte sequence is never split — with a leading `...` when anything was dropped. The newest words are the ones being spoken, and they are the ones worth the space in a small indicator. The pending text, the timer and the record of what was last shown are all cleared on a `result`, on a `state` change and on a cancel, so a new recording never opens by showing the tail of the previous one.

**Streaming is opt-in, and the REST path stays the default.** Three reasons. The realtime endpoint is a different service with its own requirements — it needs a subscription that includes realtime access, so a key that transcribes over REST can be refused there, and a default that fails for some users is a bad default. A streamed recording holds a WebSocket open for the whole hold where the REST path holds nothing between recordings, which is a larger footprint for a tool that mostly transcribes three-second utterances. And the two paths fail differently: the REST path answers a long recording by splitting it at 28 seconds and joining the pieces, while a streaming recording is one session from key press to release, with one final transcript and its own set of network failures in the middle of it. Keeping streaming off unless it is asked for leaves the file-based path — the one used and tested longest — as what happens when nothing is configured, and lets the two be reasoned about separately. `saaras:v3-realtime` is the exception that proves the rule: that model has no REST equivalent, so choosing it turns streaming on rather than producing a configuration that cannot work.

### The model must belong to the endpoint

The three endpoints do not share a model list, and the difference is not cosmetic. `saaras:v3-realtime` exists only on the realtime WebSocket endpoint and is not a REST model at all, while `saaras:v3` is a REST model that the realtime endpoint does not serve; only `saaras:v4` appears on every list. Nothing in the config file knows this. `[api] model` is a string and `[api] streaming` is a separate boolean, so a file can name a model and an endpoint that cannot be combined, and the daemon's REST transcriber sends `[api] model` verbatim, which is how a realtime model reaches an endpoint that rejects it.

So the daemon validates the model against the endpoint it is about to use, instead of letting the provider reject it. `transcriber.py` refuses a model that is not in the REST set before it touches the file or builds a client, and `streaming.py` refuses a model that is not in the realtime set before it opens the socket. Both read those sets from `config.py`, so the namespaces are written down once and there is no second copy to drift. The check sits ahead of the network call on purpose: a request that cannot succeed should cost nothing, and a model already known to be wrong must never be sent.

The error that comes out is `config_invalid`, not `api`. This is a configuration mistake rather than a service failure — nothing at the provider went wrong, and the same request would fail the same way every time — so calling it `api` would send the user to the dashboard to inspect a key and a subscription that are both fine. `config_invalid` is the code that means the settings cannot be used with the chosen model, which is exactly the situation. The message names the model, says which endpoint it belongs to, and says what to change: turn `[api] streaming` on, or choose `saaras:v4`. It carries no HTTP text at all, because the point of the check is that the user never has to read the provider's 400 to find out what to do. The same two sets back `sarvam-dictation-daemon --check`, which prints the endpoint that will be used and reports a problem when the model does not belong to it.

## Threading model

The daemon is one asyncio loop, one task per client connection, and one worker thread at a time. Everything that touches the socket is a coroutine on the loop, so message handling is naturally serialised and the state machine needs no locks. Everything that blocks — spawning the recorder, waiting for it to exit, normalising the WAV, splitting it, calling the REST API — runs inside `asyncio.to_thread`. A streaming recording is the exception, and the exception is the point: its two jobs are a pipe read and a socket read, both of which are I/O the loop can wait on directly, so it adds two tasks to the loop rather than a worker thread. That is what keeps the loop responsive while a transcription is in flight: `ping` is answered and `cancel` is accepted throughout, which is what the protocol promises.

Reading the config file on `reload` is small and does not go near the audio or the network, so it happens on the loop like any other message handler; the settings it produces are held for the next recording rather than swapped into a running one, which is what keeps a reload from racing the worker thread.

The consequence is that the daemon does one transcription at a time. That is intentional, not a limitation of the threading: one recording at a time is the protocol's rule, and serialising the API calls keeps a burst of dictation from exhausting rate limits.

## Failure modes

| Failure | Handling |
|---|---|
| Daemon not running | Addon autostarts it (if enabled), retries the connect 25 times at 200 ms, then notifies the user. |
| Daemon not found on the addon's socket path | Both sides derive the path from the same rule and read the same `[server] socket_path` from `config.toml`; a stale override left in an old fcitx5 conf is the usual cause, and the symptom is "daemon not reachable" while the daemon is visibly running. |
| Stale socket file after a daemon crash | The daemon unlinks a stale socket only after a connect attempt proves nobody is listening, so starting a second daemon cannot steal a live one's socket. |
| `config.toml` missing | Every setting falls back to its default, both at startup and on `reload`; the addon shows the defaults on the page. |
| `config.toml` unparseable or a value out of range | The daemon answers `reload` with `config_invalid` naming the key, keeps its previous settings and stays connected; the addon logs the reason and leaves its options untouched. |
| Config write fails (permissions, full disk) | `saveDaemonConfig` returns false with a reason, the addon reports it, and no `reload` is sent — the daemon keeps running on the settings it had. |
| No capture backend / wrong device | `no_audio_device` reaches the client, which shows a message pointing at the audio configuration. |
| Capture child dies or writes nothing | Zero-length or unreadable output becomes `audio_failed`; the file is discarded and the daemon returns to idle. |
| Owner disconnects mid-recording | The daemon cancels and discards the recording and returns to `idle`, so an abandoned session does not keep the microphone open. |
| Focus leaves the window mid-hold | Treated as the release that will never arrive, so the recording is finished and transcribed instead of holding the microphone open. |
| Window closes while transcribing | The trackable reference reports the input context dead; with the clipboard fallback on, the transcript goes to the clipboard and the indicator says so instead of being typed into another application. |
| Nothing focused when the transcript arrives | No context has focus, so nothing can be typed into; the transcript goes to the clipboard, or an error notification names the reason when no clipboard tool could be found. |
| A focused application discards the committed text | Not detectable — a focused input context is all the addon can see. *Always copy the transcript to the clipboard as well* covers it by copying before the commit. |
| API rejects the key or the request | The SDK exception is mapped to `api` (or `network` for transport failures) with a message that includes the underlying error but never the key. |
| Malformed line from a client | Answered with `bad_request`; the connection stays open. The addon's own parser skips bad lines and never throws into fcitx5's loop. |
| Line longer than 1 MiB | The client is disconnected; both sides enforce the same cap. |
| Streaming session fails mid-recording | Any streaming failure becomes an ordinary `error` with its own code — `no_api_key` before the socket is opened, `network` for a transport failure, `api` when the service refuses the request, `internal` for anything else — and the recording ends. No `result` follows, and the message never contains the API key. |
| Empty transcript | A legal `result` with empty text; the addon commits nothing and closes the notification. |

## Known limitations

Streaming is off by default, so out of the box there is no live interim transcript: nothing is typed until you stop recording and the whole clip has been transcribed. With `[api] streaming` on, the partial text appears in the recording indicator while you speak, but it is still not typed — the application receives one commit, when the final `result` arrives. Streaming also changes the shape of a long recording: the 28-second chunking described above belongs to the REST path, and a streamed recording is a single session from key press to release, bounded by `max_duration_s` like any other.

There is no command vocabulary. You cannot say "comma" or "new line" and get punctuation or a line break; whatever the model returns, including its own punctuation, is what gets committed. Punctuation quality therefore depends on the model and the mode.

One recording is in flight at a time, for the whole daemon, not just per client. A second client that tries to start while a recording is owned gets `busy`.

A working audio capture backend is required: one of `pw-record`, `parec` or `arecord` must be installed and must be able to open a source. The daemon does not fall back to reading the device directly.

Transcription requires network access to Sarvam's API and a valid key. Nothing about the tool works offline.

The clipboard fallback is decided on focus alone. An application that holds a focused input context but discards committed text cannot be told apart from one that accepts it, because fcitx5 gives an addon no "a text widget is focused" bit and the capability flags are too rarely advertised on X11 to stand in for one. Nothing in the addon can detect that case; the *Always copy the transcript to the clipboard as well* option is the workaround, and it has to be turned on by the user.

`config.toml` is the store for the daemon's settings and the addon's configuration page is the editor for them. The page does not merge a hand edit made while fcitx5 is running: pressing *Apply* writes the keys it manages from the values currently on the page. A hand edit made outside `fcitx5-configtool` is therefore best followed by `sarvam-dictation-ctl reload` rather than by *Apply*.

## Fcitx 5 version compatibility

The addon targets the fcitx5 **5.1.x** series, which is what Debian 12, Ubuntu 24.04 and current Fedora releases ship, and it also builds against 5.2. Three places in the code exist only because of that target:

The hotkey is registered through the runtime-typed `Instance::watchEvent(EventType, EventWatcherPhase, EventHandler)` overload and the event is then cast to `KeyEvent`. The templated `watchEvent<EventType::InputContextKeyEvent>(phase, callback)` form only appeared in 5.2.

Key matching walks the configured `KeyList` and calls `Key::check` rather than `KeyEvent::checkKeyList` with `KeyEventMatchingMode::MatchAllNormalizedKeys`, which is also 5.2-only.

`fcitx/addonmanager.h` is included from the addon header because `FCITX_ADDON_DEPENDENCY_LOADER` expands to a call on `AddonManager`, so the type has to be complete there rather than merely forward declared.

Everything else — `EventSourceIO`, `addIOEvent`, `addTimeEvent`, `EventSourceTime::setTime`, `TrackableObjectReference`, `InputContext::commitString`, the notifications module's `showTip`, and the `FCITX_CONFIGURATION`/`RawConfig` marshalling the config layer relies on — is stable across both series. The addon is compiled warning-free under `-Wall -Wextra` with C++17.
